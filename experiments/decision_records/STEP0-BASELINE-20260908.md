## 结论

第 0 阶段已完成。2.1.0 后续实验以
[`experiments/configs/baseline_2_1_0.yaml`](../configs/baseline_2_1_0.yaml)
为唯一实验基线。它把三类东西分开：

1. **当前运行时事实**：从代码入口读出的实际默认值；
2. **用户指定候选**：用户希望比较的配置，但尚未证明更好；
3. **实验决定**：只有在固定数据、指标、变量和硬门槛下运行后才能产生。

## 已解决的四个冲突

### 1. `20/5` 与 `100/10`

- 当前代码实际是：候选池 `100`，公开搜索默认最终 `Top-K=5`。
- `100/10` 是用户指定的实验候选，不是当前默认值。
- 2.1.0 先用 `100/5` 做控制组，再比较 `100/10`；没有结果前不把默认值静默改成 10。

### 2. `fixed_lines` 与 `structural_v1`

- 正式搜索入口调用 `chunk_scan_result(..., max_lines=80)`，当前正式策略是
  `fixed_lines / 80 / 0%`。
- `structural_v1` 目前只被结构切分评测脚本和单元测试调用，没有接入正式搜索入口。
- 因此它登记为候选，不再写成“当前正式 Chunk”。

### 3. `token_estimator` 状态

- 当前实现是 `UTF-8 bytes / 4` 的确定性工程近似。
- 既有真实 DeepSeek 探针证明了 usage 字段能被读取，但没有形成足够的
  “估算值 vs provider prompt_tokens”校准样本。
- 状态统一为 `pending`，不能写成已经测出最优或误差已知。

### 4. Query Rewrite 文档状态

- 当前正式运行时代码没有 Query Rewrite 实现。
- `step8_minimum_release.yaml` 的 `enabled: false` 是当前边界；旧检索矩阵中的
  `query_rewrite: [on]` 只能作为未来候选，不能作为已启用能力。
- 2.1.0 将它标为“先实现、再做 off/on 对照”，在此之前不启动该实验。
