# Q-011：Agent Run 执行队列的容量与背压

- 日期：2026-09-11
- ExperimentSpec：Q-011 Task 11（`experiments/configs/agent_run_worker_pressure.yaml`）
- 脚本：`backend/tests/evals/agent_run_queue_benchmark.py`
- Trial：2（同一 label 下的两次完整跑）
- 原始数据：`experiments/results/Q011-AGENT-RUN-QUEUE/`（不进 Git，关键数字在本页复述）

## 1. 问题

Agent Run 变成后台任务以后，需要一个「等待领取的任务最多能有多少」的取值。计划里给了
300 / 600 / 1200 三档候选和 1 / 3 / 5 秒的 queue timeout 候选，但这些是别人给的数字，
不是本项目的实验结论。这次要回答三件事：

1. 到了上限必须拒绝时，拒绝是不是真的发生、拒绝后留下什么事实；
2. 上限该取多少；
3. 排队等待由什么决定——是上限，还是别的东西。

## 2. 候选

| 候选 | 含义 |
| --- | --- |
| A：不设上限（现状） | `CODEINSIGHT_AGENT_RUN_QUEUE_LIMIT` 留空，投递不拒绝 |
| B：300 | 计划里最小的一档 |
| C：600 | 计划中间档 |
| D：1200 | 计划最大档 |
| E：queue timeout 1 / 3 / 5 秒 | **本版本没有实现**，无从对照 |

## 3. 实验

真实的部分：MySQL 事实层（`agent_runs` 表、租约 CAS、`count_queued_runs`）、
Redis broker 投递（Celery `send_task` 到 127.0.0.1:6380）、队列上限与拒绝路径。

假的部分：模型与工具**根本没有被调用**——脚本把 Run 领取后按固定占用时间
（`occupancy_ms`）直接写回 `COMPLETED`。所以这份记录只说排队与领取，不能说模型能力，
也不能说端到端吞吐。

Worker 形态：单进程 4 线程，共享一个 MySQL 事实层。

判据（跑之前定好）：拒绝必须真的发生且留下 `QUEUE_FULL` 事实；重复领取必须为 0；
被受理的 Run 不允许留在等待队列里。三条里只要有一条不成立，就是实现缺陷而不是调参问题。

## 4. 结果

两次 Trial，同一批场景（Trial 2 在 Trial 1 之后约 3 分钟）：

| 场景 | 受理 | 拒绝 | 峰值等待队列 | 排队 P95 | 重复领取 | 未收尾 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline-burst100-nolimit | 100 / 100 | 0 | 71 / 71 | 3.3s / 3.9s | 0 | 0 |
| limit300-burst100 | 100 / 100 | 0 | 77 / 75 | 3.9s / 3.4s | 0 | 0 |
| limit300-burst450 | 359 / 356 | **91 / 94** | 305 / 303 | 23.0s / 23.1s | 0 | 0 |
| limit600-burst450 | 450 / 450 | 0 | 389 / 390 | 31.2s / 31.2s | 0 | 0 |
| limit1200-burst450 | 450 / 450 | 0 | 390 / 390 | 29.7s / 31.4s | 0 | 0 |
| recovery-lease-takeover | 1 / 1 | — | — | — | 0 | 0 |

拒绝率：`limit300-burst450` 分别是 20.2% 与 20.9%。被拒的 Run 全部留下 `FAILED` +
`error_class=QUEUE_FULL` 的事实；它们没有进入队列，所以查不到变更结果——这是正确表现，
不是丢失。

租约恢复：Worker 消失后另一个 Worker 接管耗时 **57ms / 46ms**（租约一到期就接管）。

代价：

| 代价项 | 观测 |
| --- | --- |
| 受理路径延迟 | 每次投递 3–5 次 MySQL 往返；16 并发下 P50 约 0.4s，P95 约 0.9–3.5s |
| 队列上限的读放大 | 设了上限后**每次**投递都多一次 COUNT 查询（本机 P50 约 9–14ms） |
| Redis | 40 次读写 P50 6.1ms / P95 11.7ms，0 错误 |
| 收尾吞吐 | 4 个 Worker、每条占 25ms，实测 9.6–11.6 条/秒 |

## 5. 结论

**DIRECTIONAL（方向性），不是 PROVEN。**

- 背压本身成立：到达上限确实拒绝，错误类别是 `QUEUE_FULL`，拒绝留下可查事实，
  重复领取为 0，没有 Run 卡在等待队列里。这三条判据两次 Trial 都过了。
- **上限在并发下是软的**：`queue_limit=300` 时峰值观测到 305 / 303。`dispatch` 里是
  「先 COUNT 再插入」，两步之间没有原子性，16 个并发提交者会同时看到「还没满」。
  约 1.7% 的越界在容量规划里可以接受，但必须写进文档，不能声称硬上限。
- **排队等待不由上限决定**：`limit600` 与 `limit1200` 在同样 burst 下排队 P95 几乎相同
  （31.2s vs 29.7s / 31.2s vs 31.4s）。上限决定「收不收」，不决定「等多久」。
- **不属于上限的问题**：4 个 Worker 只跑出约 10 条/秒，而占用时间是 25ms；差额来自领取
  路径——它每次拉一整批再挑，队列越长单次领取越贵。当前瓶颈不是队列上限，是领取路径。

因此：**不采纳 300 / 600 / 1200 中的任何一个作为默认值**。默认保持「不设上限」，
`CODEINSIGHT_AGENT_RUN_QUEUE_LIMIT` 作为部署时的容量开关存在，取值记为
`implemented_unoptimized`（已实现、有契约、未被实验证明最优）。

## 6. 何时切换

满足下面全部条件时，再从候选值里选一个作为默认：

1. 有真实多进程 Worker（现在只有单进程多线程，进程级 CPU/内存无法归因）；
2. 领取路径不再是「拉一批再挑」，否则测出来的上限只反映领取成本；
3. 至少 5 次 Trial，且拒绝率与排队 P95 的批间波动收敛；
4. 有真实模型耗时（秒级）后的排队分布，现在的 25ms 占用与生产差距太大。

## 7. 如何回滚

把 `CODEINSIGHT_AGENT_RUN_QUEUE_LIMIT` 留空或删除即可回到「不设上限」，不需要改代码：
默认值本来就是 `None`。已经产生的 `QUEUE_FULL` 失败事实不会因此消失——它们本来就是
「当时确实被拒了」的真实记录。
