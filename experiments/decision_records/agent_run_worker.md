# Q-011：Agent Run 执行队列的容量与背压

- 日期：2026-09-11
- ExperimentSpec：Q-011 Task 11（`experiments/configs/agent_run_worker_pressure.yaml`）
- 脚本：`backend/tests/evals/agent_run_queue_benchmark.py`
- Trial：3（同一批场景连跑三次，中间不改配置）
- 原始数据：`experiments/results/Q011-AGENT-RUN-QUEUE/`（不进 Git，关键数字在本页复述）

## 1. 问题

Agent Run 变成后台任务以后，需要一个「等待领取的任务最多能有多少」的取值。计划里给了
300 / 600 / 1200 三档候选和 1 / 3 / 5 秒的 queue timeout 候选，但这些是别人给的数字，
不是本项目的实验结论。这次要回答四件事：

1. 到了上限必须拒绝时，拒绝是不是真的发生、拒绝后留下什么事实；
2. 上限该取多少；
3. 排队等待由什么决定——是上限，还是别的东西；
4. 投递本身失败（broker 不可达）时，会不会留下「已排队但永远没人执行」的假象。

## 2. 候选

| 候选 | 含义 |
| --- | --- |
| A：不设上限（现状） | `CODEINSIGHT_AGENT_RUN_QUEUE_LIMIT` 留空，投递不拒绝 |
| B：300 | 计划里最小的一档 |
| C：600 | 计划中间档 |
| D：1200 | 计划最大档 |
| E：queue timeout 1 / 3 / 5 秒 | **本版本没有实现**，无从对照 |

## 3. 实验

真实的部分：MySQL 事实层（`agent_runs` 表、租约 CAS、`count_queued_runs`）、
Redis broker 投递（Celery `send_task` 到 127.0.0.1:6380）、队列上限与拒绝路径。

假的部分：模型与工具**根本没有被调用**——脚本把 Run 领取后按固定占用时间
（`occupancy_ms`）直接写回 `COMPLETED`。所以这份记录只说排队与领取，不能说模型能力，
也不能说端到端吞吐。

Worker 形态：单进程 4 线程，共享一个 MySQL 事实层。

判据（跑之前定好）：拒绝必须真的发生且留下 `QUEUE_FULL` 事实；重复领取必须为 0；
被受理的 Run 不允许留在等待队列里；broker 不可达时不允许留下 `QUEUED`。
只要有一条不成立，就是实现缺陷而不是调参问题。

## 4. 结果

三次 Trial（Trial 3 是加了 CPU 口径与 Hard Case 之后的完整一轮）：

| 场景 | 受理（3 次） | 拒绝（3 次） | 峰值等待队列 | 排队 P95 |
| --- | --- | --- | --- | --- |
| baseline-burst100-nolimit | 100 / 100 / 100 | 0 / 0 / 0 | 71 / 71 / 72 | 3.3s / 3.9s / 3.0s |
| limit300-burst100 | 100 / 100 / 100 | 0 / 0 / 0 | 77 / 75 / 75 | 3.9s / 3.4s / 3.6s |
| limit300-burst450 | 359 / 356 / 359 | **91 / 94 / 91** | 305 / 303 / 304 | 23.0s / 23.1s / 20.2s |
| limit600-burst450 | 450 / 450 / 450 | 0 / 0 / 0 | 389 / 390 / 391 | 31.2s / 31.2s / 24.9s |
| limit1200-burst450 | 450 / 450 / 450 | 0 / 0 / 0 | 390 / 390 / 391 | 29.7s / 31.4s / 25.0s |

三次 Trial 的重复领取都是 0，未收尾都是 0。拒绝率 `limit300-burst450`：20.2% / 20.9% / 20.2%。
被拒的 Run 全部留下 `FAILED` + `error_class=QUEUE_FULL` 的事实。

Hard Case：

| 用例 | 观测 |
| --- | --- |
| 租约接管（Worker 停止续租） | 57ms / 46ms / 72ms 内被另一个 Worker 接管并跑到 `COMPLETED` |
| broker 不可达（指向没人监听的端口，20 次投递） | 10 条只读任务 `FAILED/DISPATCH_FAILED`；10 条续跑 `MANUAL_REQUIRED/DISPATCH_UNKNOWN`；**留在 QUEUED 的为 0** |

代价：

| 代价项 | 观测 |
| --- | --- |
| 受理路径延迟 | 每次投递 3–5 次 MySQL 往返；16 并发下 P50 约 0.35–0.46s，P95 约 0.7–3.4s |
| 队列上限的读放大 | 设了上限后**每次**投递多一次 COUNT 查询（本机 P50 约 9–14ms） |
| Redis | 40 次读写 P50 约 6ms / P95 约 12ms，0 错误 |
| 进程 CPU | 每受理并跑完一条 Run 约 108–116ms 的进程 CPU（单进程口径） |
| 收尾吞吐 | 4 个 Worker、每条占 25ms，实测 11–12 条/秒，远低于 4/0.025=160 条/秒 |

## 5. 结论

**DIRECTIONAL（方向性），不是 PROVEN。**

- 背压本身成立：到达上限确实拒绝，错误类别是 `QUEUE_FULL`，拒绝留下可查事实，
  重复领取为 0，没有 Run 卡在等待队列里。判据三次 Trial 全过。
- 投递失败也不会留下假象：broker 不可达时，只读任务落 `FAILED`、可能已写过工作区的
  续跑落 `MANUAL_REQUIRED`，没有一条停在 `QUEUED`。
- **上限在并发下是软的**：`queue_limit=300` 时峰值观测到 305 / 303 / 304。`dispatch`
  里是「先 COUNT 再插入」，两步之间没有原子性，16 个并发提交者会同时看到「还没满」。
  约 1.7% 的越界在容量规划里可以接受，但必须写进文档，不能声称硬上限。
- **排队等待不由上限决定**：`limit600` 与 `limit1200` 在同样 burst 下排队 P95 几乎相同
  （31.2s vs 29.7s、31.2s vs 31.4s、24.9s vs 25.0s）。上限决定「收不收」，不决定「等多久」。
- **不属于上限的问题**：4 个 Worker 只跑出约 11 条/秒，而占用时间是 25ms；差额来自领取
  路径——它每次拉一整批再挑，队列越长单次领取越贵。当前瓶颈不是队列上限，是领取路径。

因此：**不采纳 300 / 600 / 1200 中的任何一个作为默认值**。默认保持「不设上限」，
`CODEINSIGHT_AGENT_RUN_QUEUE_LIMIT` 作为部署时的容量开关存在，取值记为
`implemented_unoptimized`（已实现、有契约、未被实验证明最优）。

## 6. 何时切换

满足下面全部条件时，再从候选值里选一个作为默认：

1. 有真实多进程 Worker（现在只有单进程多线程，进程级 CPU 无法归因到某个 Worker，
   内存也没测）；
2. 领取路径不再是「拉一批再挑」，否则测出来的上限只反映领取成本；
3. Trial 数达到 5 次以上，并且补上 Redis 抖动（断开再恢复）与真实杀 Worker 进程；
4. 有真实模型耗时（秒级）后的排队分布，现在的 25ms 占用与生产差距太大。

## 7. 如何回滚

把 `CODEINSIGHT_AGENT_RUN_QUEUE_LIMIT` 留空或删除即可回到「不设上限」，不需要改代码：
默认值本来就是 `None`。已经产生的 `QUEUE_FULL` 失败事实不会因此消失——它们本来就是
「当时确实被拒了」的真实记录。
