# Q-006 / Q-007：512 token 切块与 100 token 重叠的落地结论

日期：2026-09-10
范围：`codex/2.1.0-development`
实验脚本：`experiments/chunk_parameter_probe.py`
层级：deterministic（纯测量，无模型调用，trials=1 合规）

## 问题

登记表里存着两条公开资料的常见建议：

- Q-006：chunk size 设为 512
- Q-007：overlap 设为 100

但本项目的切块器 `ingestion/chunker.py` 按**逻辑行**切分，登记单位是
`lines` 和 `ratio`；候选值分别是 `[40, 80, 120]` 和 `[0.0, 0.10, 0.20]`，
`chunk_max_lines` 的安全上限是 400 行。单位不同，直接照抄会得到 512 行的巨块。
所以必须先测量真实仓库的每行 token 密度，再把建议换算成本项目能表达的口径。

## 方法

用项目自己的 token 估算器（`domain/tokens.estimate_tokens`，即登记表 S3-P03 的
`utf8_bytes_div_4`）测量与本项目最相关的真实语料——本项目自己的
`backend/src`（110 个文件、21431 行）。空行不参与密度统计。

然后按 3×3 候选组合真实切分，统计块数量与块 token 分布。

## 结论

1. **Q-006：建议的 512 在本项目里等价于约 48.5 行，而候选集 `[40, 80, 120]`
   里没有这个值。** 40 行实测均值 334 token（偏小），80 行实测均值 599 token
   （偏大）。最接近的候选 40 与目标相差 8.5 行，属于口径差异而不是取整误差。
2. **因此不建议把 512 直接换成某个行数候选。** 正确做法是把 512 表达为
   **块级 token 上限**：新增 `max_tokens` 参数，超出上限的行块再按行细分。
   实测在 512 上限下 0 个块超限，P90 = 510、最大 = 512。
3. **Q-007：重叠 100 token 的等价比例是 0.195，与候选 0.20 吻合**，
   无需新增参数。重叠比例是无量纲量，不随行数换算漂移，可以直接采用。
4. **token 上限有真实收益**：不加上限时，当前 80 行默认配置产生 236 个超过
   512 token 的块，最大 1141 token；10 个这样的块进 Prompt 就会逼近
   `context_max_tokens=8000` 的预算。上限把最大块压到 512，代价是块数从
   328 增加到 568（索引体积增大约 73%）。

## 未完成 / 边界

- 本轮只做**参数测量**，没有做检索质量 A/B。`chunk_max_tokens=512` 是
  **工程上界**，不是「512 能提升回答质量」的结论。质量对照需要另立实验，
  且必须与 Top-K 合并口径一起定义（EXP-001 的历史教训）。
- `max_tokens` 默认 `None`，运行时行为不变。要启用需要同时升
  `chunking_version`（当前 `fixed-lines-v1`）并重建索引，因为切块结果变了。
  本轮**没有**改动运行时默认值。
- 估算器是 `utf8_bytes_div_4` 近似。对中文内容会低估（UTF-8 中文 3 字节
  → 0.75 token/字），真实供应商 tokenizer 的偏差尚未校准（登记表 S3-P03 的
  `evidence_status: pending` 依然成立）。512 作为**上界**使用是安全的：
  近似偏低意味着真实 token 可能略高于 512，若要做硬保证应下压到 480 左右。
- 语料是本项目自己的 Python 源码。换语言或换仓库需要重跑本脚本，
  密度不会自动迁移。
